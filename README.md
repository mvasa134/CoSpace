# CoSpace

Веб-сервіс бронювання робочих місць у коворкінгах: каталог коворкінгів із фільтрами, вибір місця на плані залу, бронювання й оплата, кабінети клієнта, менеджера та адміністратора.

Навчальний проєкт, група ІК-44.

## Стан проєкту

Зараз це робочий прототип: клієнт повністю готовий, а серверна частина поки що працює на тестових даних.

| Частина | Стан |
|---------|------|
| Фронтенд (`front/`) | Готовий інтерфейс: навігатор коворкінгів, фільтри, плани залів, бронювання, оплата, кабінети за ролями, теми оформлення |
| Бекенд (`back/`) | FastAPI з мок-даними: логін, профіль, коворкінги й місця, створення бронювання, оплата |
| База даних | Схема, міграція, збережені процедури та скрипт розгортання для Azure SQL (див. розділ «База даних») |
| Підключення API до БД, справжні JWT і 2FA | У планах |

Функції, для яких на бекенді ще немає ендпоінтів (список і скасування бронювань, закриття столів, заявки менеджерів, список користувачів, журнал), клієнт виконує локально, у пам'яті сторінки.

## Ролі

| Роль | Можливості |
|------|------------|
| Client | Пошук і бронювання місць, перегляд своїх бронювань, оплата, скасування, редагування профілю |
| SpaceManager | Усе, що Client, а також керування власними коворкінгами, місцями й планом, чорний список, підтвердження й завершення бронювань, повернення коштів |
| PlatformAdmin | Усе, що SpaceManager, а також керування користувачами (ролі, блокування, видалення), призначення менеджерів, перегляд аудит-логу |

## Технології

| Шар | Технології |
|-----|------------|
| Frontend | HTML, CSS, JavaScript (без збирача та фреймворків) |
| Backend | Python 3.11+, FastAPI, Pydantic, Uvicorn |

## Встановлення та запуск

### Потрібно

- Python 3.11+
- сучасний браузер

### Бекенд

```bash
git clone https://github.com/mvasa134/CoSpace.git
cd CoSpace/back
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

API працює на http://127.0.0.1:8000, інтерактивна документація (Swagger UI) за адресою http://127.0.0.1:8000/docs, перевірка стану: `GET /`.

### Фронтенд

Клієнт це статичні файли, збирати їх не потрібно. Запустіть будь-який статичний сервер у папці `front/`:

```bash
cd CoSpace/front
python -m http.server 3000
```

Відкрийте http://localhost:3000. Адресу API задано константою `API_BASE` на початку блоку «persistence» у `app.js` (за замовчуванням `http://127.0.0.1:8000`), тож бекенд має працювати на цій адресі.

### Тестовий вхід

Мок-автентифікація приймає будь-які непорожні логін і пароль. Усі запити виконуються від імені тестового користувача.

## API

Поточні ендпоінти (тестові дані):

| Метод | Шлях | Опис |
|-------|------|------|
| GET | `/` | Перевірка стану сервісу |
| POST | `/auth/login` | Вхід (форма `username`, `password`), повертає токен |
| GET | `/auth/me` | Профіль поточного користувача (потрібен токен) |
| GET | `/coworkings` | Список коворкінгів із робочими місцями |
| GET | `/coworkings/{id}` | Один коворкінг |
| GET | `/coworkings/{id}/workspaces?floor=` | Місця коворкінгу, з фільтром за поверхом (1–7) |
| POST | `/bookings` | Створити бронювання (потрібен токен) |
| POST | `/payments/process` | Провести оплату, повертає квитанцію |

Токен передається в заголовку `Authorization: Bearer <token>`. Тіло `POST /bookings`: `workspace_id`, `booking_type` (`hourly`, `daily` або `monthly`), `start_time`, `duration`. Тіло `POST /payments/process`: `booking_id`, `amount`, `payment_method`. Точні схеми дивіться у Swagger UI.

Помилки повертаються у форматі `{ "detail": "Текст повідомлення" }`.

## База даних

База даних готова окремо від прототипу API і розгортається на Azure SQL (підходить і локальний SQL Server). Уся робота з БД задумана через збережені процедури, raw SQL у застосунку не використовується.

### Склад

Десять таблиць: `Users`, `UserAuth` (хеш пароля й TOTP, зв'язок 1:1 з `Users`), `UserRecoveryCode`, `EmailToken`, `AuditLog`, `Coworking`, `Workspace`, `Blacklist`, `Booking`, `Payment`.

Ключові рішення:

- **Тригер `TR_Booking_NoOverlap`** забороняє перетин активних бронювань (Pending, Confirmed) одного місця. Інтервали напіввідкриті: бронювання 10:00–11:00 і 11:00–12:00 не конфліктують.
- **Обмеження `CHECK`** гарантують допустимі ролі й статуси, `EndTime > StartTime`, невід'ємні ціни та суми, а також те, що 2FA не вмикається без секрету.
- **Каскадні видалення** лише для композицій (місця коворкінгу, оплата бронювання, дані автентифікації). Історія (бронювання, аудит, менеджерство) не видаляється: користувача блокують, місце закривають для бронювання.
- **Секрети** (паролі, резервні коди, email-токени) зберігаються лише як хеші, TOTP-секрети лише у зашифрованому вигляді.
- Статуси бронювання: `Pending → Confirmed → Completed`, скасування можливе з `Pending` та `Confirmed`. Сума оплати рахується в БД: тривалість у годинах × ціна за годину.

### Збережені процедури

Близько п'ятдесяти процедур `usp_*`, згрупованих за сутностями: User, Auth, RecoveryCode, AuditLog, Coworking, Workspace, Blacklist, Booking, Payment, EmailToken. Помилки повертаються через `THROW` з кодами:

| Код | Значення |
|-----|----------|
| 50001 | користувача заблоковано |
| 50002 | користувач у чорному списку коворкінгу |
| 50003 | місце закрите для бронювання |
| 50004 | запис не знайдено |
| 50010 | email уже зайнятий |
| 50011 | недопустимий перехід статусу |
| 50012 | є залежні записи (бронювання, історія) |
| 50013 | оплата вже існує |
| 50020 | занадто часті листи (cooldown) |

### Розгортання

Порядок виконання файлів: `coworking_db.sql` → `002_email_verification.sql` → `coworking_procedures.sql`. Усе це робить скрипт:

```bash
pip install pyodbc python-dotenv
python db/deploy_db.py                # схема (якщо ще немає) + міграція + процедури
python db/deploy_db.py --procs-only   # лише процедури (CREATE OR ALTER, можна повторювати)
python db/deploy_db.py --app-user     # додатково створити користувача coworking_api (лише EXECUTE)
```

Скрипт можна запускати повторно: якщо таблиця `dbo.Users` уже існує, `coworking_db.sql` пропускається, а міграція та процедури ідемпотентні.

Потрібен Microsoft ODBC Driver 18 for SQL Server. Параметри підключення задаються у файлі `.env` у корені проєкту:

| Змінна | Обов'язкова | Опис |
|--------|-------------|------|
| `DB_SERVER` | так | Адреса сервера (для Azure SQL FQDN сервера, для Express `localhost\SQLEXPRESS`) |
| `DB_NAME` | ні | Ім'я бази даних (за замовчуванням `CoworkingDB`) |
| `DB_USER` | так | Логін SQL-автентифікації |
| `DB_PASSWORD` | так | Пароль SQL-автентифікації |
| `DB_DRIVER` | ні | ODBC-драйвер (за замовчуванням `ODBC Driver 18 for SQL Server`) |
| `DB_TRUST_CERT` | ні | `true` для локального сервера із самопідписаним сертифікатом |
| `APP_DB_PASSWORD` | для `--app-user` | Пароль користувача `coworking_api` |

Користувач `coworking_api` не має прямого доступу до таблиць, лише право виконувати процедури.

### Налаштування Azure SQL

1. Створіть порожню базу, наприклад `CoworkingDB`.
2. У Azure Portal відкрийте SQL Server, розділ Networking, і додайте свій IP у firewall.
3. На рівні Serverless перше підключення після простою може тривати близько хвилини.
4. Запустіть `python db/deploy_db.py`.

### Імпорт готової бази (.bacpac)

Якщо базу передали файлом `.bacpac`, розгортати схему скриптом не потрібно. Імпортуйте файл у SSMS (**Databases → Import Data-tier Application**) або через `sqlpackage`:

```bash
sqlpackage /Action:Import /SourceFile:"CoworkingDB.bacpac" \
  /TargetConnectionString:"Server=localhost;Database=CoworkingDB;User Id=sa;Password=<пароль>;Encrypt=True;TrustServerCertificate=True"
```
