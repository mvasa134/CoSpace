# README

# CoSpace

Веб-сервіс для пошуку та бронювання робочих місць у коворкінгах. Клієнт обирає коворкінг, бачить план залу, бронює вільне місце на потрібний час і оплачує його. Менеджер керує своїм коворкінгом, а адміністратор платформою загалом.

Робоча версія: [https://cospace-api.fly.dev](https://cospace-api.fly.dev/)
Документація API (Swagger UI): [https://cospace-api.fly.dev/docs](https://cospace-api.fly.dev/docs)

## Можливості

- реєстрація з підтвердженням email, вхід, скидання та зміна пароля
- двофакторна автентифікація (Google Authenticator, TOTP) з резервними кодами
- каталог коворкінгів із фільтрами та інтерактивними планами залів
- бронювання місця на вибраний час з перевіркою годин роботи, максимальної тривалості та перетину з іншими бронюваннями
- оплата бронювання (навчальна імітація платіжного шлюзу), повернення коштів
- кабінети за ролями: клієнт, менеджер коворкінгу, адміністратор платформи
- чорний список клієнтів для окремого коворкінгу
- журнал дій (аудит-лог)

## Ролі

| Роль | Можливості |
| --- | --- |
| **Client** | Пошук і бронювання місць, оплата, перегляд і скасування своїх бронювань, налаштування профілю та 2FA |
| **SpaceManager** | Усе, що Client, а також створення та керування своїм коворкінгом: місця, план залу, години роботи й ліміти тривалості, підтвердження й завершення бронювань, повернення коштів, чорний список |
| **PlatformAdmin** | Усе, що SpaceManager, для будь-якого коворкінгу, а також призначення менеджерів, керування користувачами (ролі, блокування, видалення), перегляд аудит-логу |

## Архітектура

Модульний моноліт із трьох частин:

```
Браузер (front/)  ──HTTP/JSON──▶  FastAPI (back/app)  ──pyodbc──▶  Azure SQL (процедури usp_*)
```

- **Фронтенд** складається зі статичних сторінок, які віддає сам бекенд: `/` (клієнт), `/manager` (панель менеджера), `/admin` (панель адміністратора). Стилі й скрипти віддаються за адресою `/static/...`.
- **Бекенд** — це REST API, поділений на модулі: `auth`, `users`, `coworkings`, `bookings`, `audit`. Роутери перевіряють права й вхідні дані, а вся робота з даними йде через збережені процедури.
- **База даних** містить цілісність і бізнес-правила (перетин бронювань, допустимі переходи статусів, розрахунок суми). Застосунок не виконує довільних SQL-запитів до таблиць.

Детальний опис архітектури й вимог лежить у папці `docs/`.

## Запуск локально

### Потрібно

- Python 3.11+
- [Microsoft ODBC Driver 18 for SQL Server](https://learn.microsoft.com/sql/connect/odbc/download-odbc-driver-for-sql-server)
- доступ до бази Azure SQL або локального SQL Server (див. розділ «База даних»)

### Кроки

```bash
git clone https://github.com/mvasa134/CoSpace.git
cd CoSpace

# 1. налаштування
cp .env.example .env              # Windows: copy .env.example .env

# 2. залежності
python -m venv .venv
source .venv/bin/activate         # Windows: .venv\Scripts\activate
pip install -r back/requirements.txt

# 3. запуск
cd back
uvicorn app.main:app --reload
```

Після запуску:

- сайт: [http://127.0.0.1:8000](http://127.0.0.1:8000/)
- панель менеджера: [http://127.0.0.1:8000/manager](http://127.0.0.1:8000/manager)
- панель адміністратора: [http://127.0.0.1:8000/admin](http://127.0.0.1:8000/admin)
- Swagger UI: [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs)
- перевірка стану й підключення до БД: [http://127.0.0.1:8000/health](http://127.0.0.1:8000/health)

Ключі для `.env` можна згенерувати так:

```bash
python -c "import secrets;print(secrets.token_urlsafe(48))"                               # JWT_SECRET
python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"  # TOTP_ENC_KEY
```

Якщо `SMTP_HOST` порожній, листи не надсилаються, а друкуються в лог сервера. Це зручно для локальної розробки: посилання для підтвердження email можна взяти з консолі.

## API

Усі запити, крім реєстрації, входу й відновлення пароля, вимагають заголовок `Authorization: Bearer <token>`. Помилки повертаються у форматі `{ "detail": "Текст повідомлення" }`. Повні схеми запитів і відповідей описані у Swagger UI (`/docs`).

### Автентифікація: `/auth`

| Метод | Шлях | Опис |
| --- | --- | --- |
| POST | `/auth/register` | Реєстрація (email, пароль від 8 символів), надсилає лист для підтвердження |
| POST | `/auth/login` | Вхід; за увімкненої 2FA додатково потрібен `totp_code` або `recovery_code` |
| POST | `/auth/verify-email` | Підтвердження email за токеном з листа |
| POST | `/auth/resend-verification` | Повторно надіслати лист |

| POST | `/auth/reset-password` | Встановити новий пароль за токеном |

### Правила бронювання

- Бронювання можливе лише в години роботи коворкінгу (за замовчуванням 10:00–22:00).
- Максимальна тривалість окрема для звичайних місць (за замовчуванням 3 год) і переговорних кімнат (за замовчуванням 12 год). Менеджер змінює ці параметри в налаштуваннях коворкінгу.
- Активні бронювання одного місця не можуть перетинатися. Бронювання 10:00–11:00 і 11:00–12:00 конфлікту не створюють.
- Статуси бронювання: `Pending → Confirmed → Completed`. Скасувати (`Cancelled`) можна з `Pending` або `Confirmed`.
- Статуси оплати: `Pending → Paid / Failed`, `Paid → Refunded`. Сума рахується в БД: тривалість у годинах × ціна за годину.
- Клієнт із чорного списку коворкінгу та заблокований користувач не можуть бронювати.

## База даних

Робоча база розгорнута в Azure SQL, і застосунок працює з нею лише через збережені процедури. Дані підключення не зберігаються в репозиторії: їх задають у `.env` локально та через `fly secrets` на сервері.

Скрипти в папці `db/` містять основну схему: користувачі, автентифікація, коворкінги, місця, чорний список, бронювання, оплата, аудит. Таблиці та процедури для налаштувань коворкінгу й плану залу (`usp_Settings_*`, `usp_Layout_*`, `usp_Shape_*`) є лише в робочій базі на Azure. Тому на базі, розгорнутій тільки з цих скриптів, бекенд запуститься, але налаштування годин роботи й редактор плану залу працювати не будуть.

### Склад

Таблиці: `Users`, `UserAuth` (хеш пароля й TOTP, 1:1 з `Users`), `UserRecoveryCode`, `EmailToken`, `AuditLog`, `Coworking`, `Workspace`, `Blacklist`, `Booking`, `Payment`.

Ключові рішення:

- **Тригер `TR_Booking_NoOverlap`** забороняє перетин активних бронювань (`Pending`, `Confirmed`) одного місця.
- **Обмеження `CHECK`** гарантують допустимі ролі та статуси, `EndTime > StartTime`, невід’ємні ціни й суми, а також те, що 2FA не вмикається без секрету.
- **Каскадні видалення** застосовано лише для композицій (місця коворкінгу, оплата бронювання, дані автентифікації). Історія (бронювання, аудит) не видаляється: користувача блокують, а місце закривають для бронювання.
- **Секрети** (паролі, резервні коди, email-токени) зберігаються лише як хеші, TOTP-секрети лише в зашифрованому вигляді.

### Збережені процедури

Понад п’ятдесят процедур `usp_*`, згрупованих за сутностями: User, Auth, RecoveryCode, AuditLog, Coworking, Workspace, Blacklist, Booking, Payment, EmailToken. Помилки повертаються через `THROW` з кодами:

| Код | Значення |
| --- | --- |
| 50001 | користувача заблоковано |
| 50002 | користувач у чорному списку коворкінгу |
| 50003 | місце закрите для бронювання |
| 50004 | запис не знайдено |
| 50010 | email уже зайнятий |
| 50011 | недопустимий перехід статусу |
| 50012 | є залежні записи (бронювання, історія) |
| 50013 | оплата вже існує |
| 50020 | занадто часті листи (cooldown) |

## Тестування

Автоматичні тести покривають автентифікацію, 2FA, користувачів, коворкінги, бронювання, оплату, аудит, налаштування, безпеку, схеми даних і надсилання пошти. Тести не потребують справжньої бази: виклики процедур підміняються моками.

```bash
pip install -r back/requirements.txt -r tests/requirements-test.txt
pytest                      # з кореня репозиторію
```

## Розгортання

Застосунок розгорнутий на Fly.io одним Docker-образом, у якому бекенд разом зі сторінками фронтенду. Команду треба запускати з кореня репозиторію:

```bash
fly secrets set DB_SERVER=... DB_USER=... DB_PASSWORD=... JWT_SECRET=... TOTP_ENC_KEY=...   # один раз
fly deploy
```

Секрети задаються через `fly secrets`, а не в `fly.toml`. Машина зупиняється без запитів і запускається автоматично при першому зверненні, тому перша відповідь після простою може бути повільнішою.

## Командна робота

- Основна гілка `main` містить стабільну версію проєкту. Зміни потрапляють у неї лише через Pull Request.
- Кожна частина проєкту має свою гілку й папку: `back` → `back/`, `front` → `front/`, `db` → `db/`, `tests` → `tests/`.
- Pull Request містить короткий опис змін. Злиття відбувається після перегляду кимось із команди.
